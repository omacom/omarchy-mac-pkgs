# Retiring a Touch ID experiment

`touchid-transition.py` applies a separately reviewed, hash-pinned configuration plan and keeps an exact inverse. This is a standalone migration, not package setup. It never opens a sensor, writes SEP files, changes enrollment, restarts services, changes a boot default or uninstalls packages.

## Intended operator and transition

The proposed operator is a developer or administrator retiring an earlier experimental Touch ID installation, once the replacement kernel and provider have been installed, booted and qualified. For example, that installation may have experimental PAM includes, release-specific loader-unit overrides and module options that must be replaced together without losing a password fallback. Another supported plan only records package-owned consent for an already restored, working experimental installation. That narrower phase cannot edit PAM or authorize new enrollment.

The operator prepares and reviews the complete before/after plan for that installation, runs `check`, and applies it from an attended root terminal with a private checkpoint. An interrupted transition is rolled back from that checkpoint before retrying. There is no automatic plan generator, shipped machine-specific plan, package hook or ordinary-user setup invocation. A stock installation using the supported package entrypoints does not need this migration.

The runtime's enable-fingerprint/disable-fingerprint commands remain the owner-facing authentication setup controls. The package's `touchid-enable`, `touchid-status` and `touchid-activate` helpers handle consent, driver startup and readiness. This proposal does not replace those controls: it journals a separately reviewed, one-time configuration conversion and its exact inverse. The passive `touchid-recovery` report supplies facts to that conversion; it does not repair enclave state. General M1 enablement, enrollment recovery and anti-replay ownership remain separate work.

Whether this separate tool should be maintained upstream is an open design question. The existing experimental-installation use case does not establish demand from stock package users. Keep the proposal in draft until maintainers agree on the operator workflow and on the boundary with the existing entrypoints. Its live gate also needs the kernel's `host_store` diagnostic, whose companion change is not yet submitted; passing filesystem transaction tests alone does not make the migration deployable.

## Plan and execution

A plan names only PAM, systemd, modprobe and Mac-consent configuration. It records the old hash/mode/owner, the complete proposed new bytes, the required kernel release and the hashes of installed replacements. A live apply additionally requires an attended root terminal, `--live`, the matching running kernel/module and the passive report from `omarchy-mac`'s `/usr/lib/omarchy-mac/touchid-recovery`. That program ships in `omarchy-mac`. Apply checks that it is executable and, before changing configuration, stops and names that path when the program is missing, exits non-zero, or prints something other than one JSON object. Its `action` is `ready-for-test` only when `/dev/sep-bio` is present and the driver's diag attributes show xART writes enabled, the sensor online, Touch ID ready, the sensor attached, a restored or empty enrollment, a usable or unverified match path, an open key store with a present identity keybag and no xART-guard refusals. The report never opens the node. A `preserve-existing-consent` plan still requires its stricter facts, including `restore` of `restored`, `matching` of `usable` and `refusals` of 0. The plan must pin `/sys/module/apple_sep/notes/.note.gnu.build-id`, not rely on a release name alone. New package files must already be installed and the new kernel booted before the authentication transition. Password login remains available until the attended test is completed. A preboot plan may preserve existing consent only for the two absent package-owned consent/options files, on the pinned working kernel with a restored, usable sensor and no guard refusals; it cannot change PAM or authorize a new enrollment.

Use `check`, `apply` or `rollback`, each with `--plan FILE --checkpoint DIRECTORY`. The checkpoint must be a new directory for apply. `--root PATH` is for an isolated test image and never implies a live transition. Apply validates every old file and new payload before changing anything; each atomic replacement is journalled and flushed. The journal and every containing directory entry in its checkpoint path are synchronized before the first configuration replacement; a failed checkpoint synchronization leaves configuration untouched. A directory the transition creates is synchronized in its parent before the transition is recorded applied, and a failure of that synchronization rolls the transition back. One lock under the target root, `run/omarchy-mac/touchid-transition.lock`, covers every checkpoint for that root. An error during replacement attempts the exact inverse. Rollback refuses to overwrite an administrator's intervening edits. If power is lost, run rollback with the same plan/checkpoint before attempting another transition. Keep the checkpoint private: it contains configuration, though it never contains fingerprint or enclave data.

The local plan removes experimental artifact gates after the replacement driver/provider are ready, preserves account restrictions, retains sudo's TTY condition with `pam_succeed_if`, and uses the separate parallel SDDM fingerprint service. It overrides the older support package's vendor drop-in by basename until that package is retired. Other distributions need their own reviewed PAM policy; this tool does not invent one.

After the positive/negative/password and lid checks pass, remove obsolete integration/support packages with the package manager, retaining their archives for rollback. Do not delete package-owned files by hand. Before retiring unowned release-specific loader units, verify their hashes and confirm that no remaining unit requires them. Keep old-kernel fallback loaders until the replacement cold boot is accepted. Publication and general M1 activation remain separate approvals and evidence boundaries.

Run `python3 -B tools/migration/test/transition-test.py`. The suite exercises real temporary-file transactions, each injected interruption, exact rollback, drift refusal, symlink handling, forbidden state paths, administrator changes, created-directory durability, one lock per target root and the readiness command. These are not PAM authentication or physical persistence results.

The passive readiness report requires the kernel's actual `host_store` diagnostic, an open keystore and a present keybag from the same bound device. Missing host-store diagnostics fail closed; older kernels need the host-store-readiness companion before a live transition can qualify.
