# omarchy-mac

Apple Silicon defaults and support services for Omarchy. Version: `0.2.4` (candidate). This add-on complements `omarchy` and `omarchy-settings`; it selects no kernel and contains no installer or repository trust configuration. It covers what stays on an installed Mac; installing one is the job of the [Omarchy Installer](https://github.com/omacom/omarchy-mac-installer), and boot support is the separate `omarchy-mac-boot` package beside this one.

## Build and stage

This directory is self-contained. Copy it anywhere, run `./test/all`, then `./install /absolute/staging/root`. Staging requires Bash, coreutils and findutils; tests also use Python and systemd. Nothing is enabled or started by staging. Its Arch recipe lives in [omacom/omarchy-pkgs](https://github.com/omacom/omarchy-pkgs) and pins a full commit of this repository.

Runtime dependencies: `omarchy` (the `omarchy-hw-platform` detector and its Apple predicate), Bash, coreutils, grep, sed, gawk, systemd, pciutils, kmod, mkinitcpio, NetworkManager, iwd, Python, PipeWire, pipewire-pulse, libpulse (pactl, parec), WirePlumber, the protected Asahi speaker stack: asahi-audio, speakersafetyd (whose unit this package presets), alsa-ucm-conf-asahi, rtkit and pipewire-alsa; vulkan-asahi, the GPU's Vulkan driver; and asahi-alarm-keyring, for the Asahi repository Omarchy's Apple Silicon pacman template configures. Upgrading this package brings all of them to machines set up before it named them. The hardware video decode stack (avd-fw, libva-v4l2_request-avd), wf-recorder and widevine are defaults in the runtime's Apple package list instead, which an owner may remove. See `ORIGINS.md` for extraction attribution.

## Setup contract

Upgrade the matching runtime, settings and add-on candidates in one pacman transaction. Their transferred commands and user unit must have only one owner. A fresh Apple Silicon install takes two transactions before `omarchy-apply-system`: first one that installs the settings package, then one that installs the platform's default set (`omarchy-pkg-defaults aarch64-apple`: the base, aarch64 and Apple lists, this add-on included). The settings package's pacman platform guard checks only transactions that start after it is installed, so no Apple package may share a transaction with it; the runtime can go in either. The recipe must tag this package with `groups=('omarchy-platform-apple-silicon')`; the desktop's `docs/platform-guard.md` has the contract. The desktop's last hardware leaf runs this package's system setup through the dispatcher, and offline setup never downloads it: a Mac without it keeps Omarchy's generic setup.

Run `omarchy-mac-setup-system` as root on the target hardware (inside its target chroot for offline provisioning). An optional absolute root argument supports staging against the same target hardware without a bus. It exits without changes unless the runtime's Apple predicate `omarchy-hw-apple-silicon` holds (`omarchy-hw-platform` reports `aarch64-apple`, or `apple-silicon` on a runtime from before the platform rename), and fails if the detector does. It removes the Intel Mac Broadcom quirk (`options brcmfmac feature_disable=0x82000`, which breaks Apple Silicon Wi-Fi) from `/etc/modprobe.d/brcmfmac.conf` wherever an unguarded runtime migration appended it: only that exact line, with the comment block and blank line written right above it, goes; the file goes when nothing but blank lines is left, a link is left alone with the manual fix, and the initramfs rebuild it owes is recorded under `/var/lib/omarchy/migrations/1789172112-initramfs-pending`, which the runtime's migration finishes. It replaces `/etc/mpv/mpv.conf` with the current mpv default only while it is a regular file byte-identical to the earlier default, which lacks `gpu-sw=yes`; an edited copy or a link stays. It enables resume recovery only for BCM4378, BCM4387 and BCM4388 on Apple Silicon; Intel/T2 Macs are excluded. It is the only enabler of `speakersafetyd`, without which the kernel keeps the speakers muted: it applies the package's `80-omarchy-mac-audio.preset` once speakersafetyd is installed, so `/etc` presets that sort before it or replace it by name, masks and later explicit disables win, and image builders that apply presets get the same result. A live run also restarts a speakersafetyd left dead by a start-limit. No NetworkManager restart or driver reload occurs during setup. The backend applies when NetworkManager next starts; notch changes apply when appledrm next loads. A live run gives iwd a profile for each Wi-Fi network NetworkManager saved with its key before the switch, as NetworkManager itself does for a new connection, so saved networks keep connecting instead of reading as a wrong password. The greeter drop-in needs no setup: from the next `sddm` start it holds the greeter, for at most 10 s, until Apple's display controller has replaced the boot framebuffer.

Run `omarchy-mac-setup-user` as each target user with their HOME/XDG directories. It enables the vendor unit without a session bus. It writes nothing into the user's Hyprland files; a block an earlier version appended to `input.lua` or `looknfeel.lua` stays, as the user's. With a live bus, reached only through XDG_RUNTIME_DIR (which `sudo -i` clears), it reloads the user manager, reports the effective unit and starts the mapper. The mapper makes the microphone a typed stereo source, `omarchy_asahi_mic` ("MacBook Microphone"): pipewire-pulse's `module-remap-source` records asahi-audio's mono DSP source (its AUX0 or MONO port), which WirePlumber links to the left side and the mapper to the right, or to a single MONO capture port when PipeWire negotiates one, and offers an `Audio/Source` with front-left and front-right, the shape of a stock microphone, so the desktop's audio panel drives its volume, mute and level meter as it does any other. It makes that source the default input only if a brief sample finds signal, and hands a silent one back to the DSP source. A muted mapping is the user's microphone mute and is left alone. On upgrade from 0.1.2 the mapper replaces 0.1.2's virtual source of the same name (an `Audio/Source/Virtual`, which the panel gives no level meter), keeping its gain, mute and selection. pacman restarts no user service, so a running mapper watches its own file: once an upgrade has replaced it and the transaction has ended, it runs the new file in place, within a few seconds, and that reconciles the live session. At session start the mapper subscribes to audio events before its first pass, so a DSP microphone that appears after it starts is mapped and made the default input at once. Provisioning and first run call setup; subsequent session starts only start the enabled unit, without reloading the user manager or repeating setup. The first desktop session does not depend on a bus existing during installation. Custom fragments, masks, activation links and headset or speaker policies are preserved; setup markers preserve explicit disables after initial setup. User gain state remains in `omarchy/asahi-mic-gain.json` under XDG_STATE_HOME. The desktop saves that state before restarting audio.

A runtime whose `omarchy-lifecycle-dispatch` has the `setup-system` and `setup-user` operations (the platform setup seam, which registers `/usr/lib/omarchy/mac` for Apple Silicon) reaches both through the entrypoints this package stages there; an older runtime calls the two commands itself: `setup-system [image-first-boot]` (root, from the last hardware leaf and on an image's first boot, where it downloads nothing; it rebuilds no boot file) and `setup-user` (as the user being set up, at finalization and again in first run). Each re-checks the platform.

System setup also wraps Chromium, 1Password and Cursor where they are installed: without the GPU driver an Apple Silicon Mac has no DRM render node and their GPU process fails, so the runtime's `omarchy-cmd-electron-gl-wrap` puts a wrapper in `/usr/local/bin` that passes software GL flags only while no render node exists; a launcher an administrator owns is kept. A runtime without `omarchy-cmd-electron-gl-wrap` creates no new wrappers (both setup halves skip; existing ones stay), and one without `omarchy-cmd-desktop-exec-repair` leaves the desktop entries alone. User setup points the user's own desktop entries for them at a ready wrapper (`omarchy-cmd-desktop-exec-repair`) and turns `AcceleratedVideoDecoder` off in each Chromium-family `*-flags.conf`, joining an existing `--disable-features` list: Brave and other VA-API builds render green frames through the Apple Video Decoder, while mpv, ffmpeg and GStreamer keep it. A browser install runs user setup again after it writes a fresh flags file. Where Steam is installed, system setup also installs `omarchy-steam-fex` (Steam runs x86 under FEX in a muvm VM) from the configured repositories, and user setup runs its `omarchy-launch-steam --prepare` for a user who has Steam; the runtime's Steam installer reaches both through the dispatcher. These and the Electron steps need the live machine, so a staging root skips them.

The Mac's hardware data lives in the platform root, `/usr/share/omarchy-platform`, which Omarchy reads at that fixed path and ships nothing in, so Omarchy's own config carries no Apple branch. All of it is data. The package ships no Hyprland files and changes no Hyprland binds or settings: Omarchy's binds, trackpad and cursor defaults apply on a Mac as on any other machine. A key the built-in keyboard lacks is given to it below Hyprland, as a udev hwdb remap in this package (omacom/omarchy-mac-pkgs#6, in review).

- `key-names`: the keybindings menu shows `XF86MonBrightnessUp` and `Down` as the F2 and F1 they are.
- `display-cutouts.json`: the notch of each MacBook panel (the 14" Pro measured at 64 physical rows, the 16" Pro inferred at 64 and the Airs at 56), which the bar keeps clear of. A notched panel not listed gets no floor until the file lists it; `[bar] notch-height` in `shell.toml` only adjusts the floor of a listed panel.
- `displays.conf`: `omarchy-hw-display` never picks the Touch Bar's `display-pipe` or `228600000.dsi.0` backlight and prefers the Retina panel's `apple-panel-bl` (no GPU backlight exists), and `omarchy-brightness-display` probes an external monitor over DDC only when its connector has a `ddc` node, since Apple's display driver registers no DDC channel and a probe would walk the SoC's SMBus for about 3 s.
- `audio.json`: the audio panel and microphone widget leave out asahi-audio's DSP internals: the speaker graph's output stream into the raw speakers (`effect_output.jNNN-convolver`, and the desktops' `mini`/`studio`), the microphone graph's always-running capture of the raw array (`audio_effect.jNNN-mic`), the raw devices asahi-audio marks do-not-use (`RawSpeakers`, `RawMics`), the mapper's own capture of the DSP microphone (`input.omarchy_asahi_mic`), which would otherwise count as an app recording, and the mono DSP microphone while the mapper's stereo `omarchy_asahi_mic` exists. A runtime older than the platform root reads no audio hints and keeps its own Apple checks.
- `fingerprint-readers`: Touch ID. `omarchy-hw-fingerprint` finds the sensor once `/run/omarchy-mac/touchid` reads `ready`, or `available` before the owner has turned it on. Nothing loads the Secure Enclave driver until the owner agrees. At boot, `omarchy-mac-touchid-status.service` (`lib/touchid-status`, pulled in by the package's `multi-user.target.wants` link, before the greeter and `fprintd`) asks `lib/touchid-eligibility`, which reads only the device tree and installed files: `available` needs a sensor node, a board the aurora driver has a profile for (M2, M2 Pro and Max, the M3 Air J613 and J615, and the MacBook Neo; M1-family Macs wait for their xART guard path), `/chosen/apfs-preboot-uuid`, a way to the calibration (under the name the sensor's `firmware-name` gives, `apple/mesacal-<board>.bin`, or `apple/mesa_calibration.bin` on M2 Pro and Max) and, on the Neo, a way to the sensor root key, an installed one or the factory records on the ESP with `python` to rebuild it from (the extractors need `python`, which linux-aurora only suggests), and an Omarchy whose `omarchy-lifecycle-dispatch` resolves `enable-fingerprint`, since the invitation comes once and an older setup would enrol a reader nothing turned on; anything else records `unsupported:<reason>`, which no detector line names. Omarchy's fingerprint setup then runs `omarchy-lifecycle-dispatch enable-fingerprint` (`entrypoints/enable-fingerprint`, as root) before enrolling. With no status file (a Mac without a sensor records nothing, and a status service can fail) it works eligibility out again. Where Touch ID can't be set up it lets the setup go on, so a USB reader enrols on a Mac mini, a Studio or an M1 Mac as it would without Touch ID. A Mac whose owner already agreed is never asked again: it gets any missing options and, unless Touch ID reads `ready`, is told to restart, and the setup goes on. It stops the setup only when the owner says no, or turning Touch ID on or writing its options fails. It says what the owner is agreeing to: the key store Linux creates stays, the enclave's anti-replay state moves forward and is one file in the iBoot System Container that macOS updates too, and a bug that writes it wrongly can cost macOS data (with FileVault on, macOS won't start and the Mac needs a DFU restore; with FileVault off, macOS resets its keychain and fingerprints), so back up macOS first. It names the Neo's sensor key only on a Neo, and an earlier key store only where one exists, and asks. FileVault's state isn't checked: the owner can change it after installing, so both cases are always named. On yes, `lib/touchid-enable` carves what is missing from this Mac's own iBoot System Container into `/usr/lib/firmware/updates` (the calibration with linux-aurora's `extract-mesa-calibration`, except on the Neo, whose installer writes the sealed form; the Neo's `apple/msrk-j700.bin`, root-only `0600`, rebuilt with `lib/touchid-root-key`), records the agreement in `/etc/omarchy-mac/touchid-on` and in the driver's options (`/etc/modprobe.d/omarchy-mac-touchid.conf`: `xart_writes=1 provision_keybag=1`, today's defaults, which a kernel that loads `apple_sep` read-only by default, omacom/linux-aurora#180, writes only with; the name sorts after `apple-sep.conf`, so the owner's agreement wins over any `apple-sep.conf`, while `apple_sep.xart_writes=0` on the kernel command line still wins over both, and no initramfs hook includes `apple_sep`, so only the root's copy of the options is read), loads `apple-sep` now (a driver already running keeps the options it loaded with, so on a kernel that loads it read-only, and a Mac with no key store yet, the agreement stands and Touch ID turns on after a restart), and succeeds only once the activation records `ready`, restarting an `fprintd` that started without the reader; a failure after the record is written removes it again, so the next boot offers Touch ID again instead of loading a driver that never came up. A driver that loaded but never came up stays that way until a restart, so the status then reads `failed` and setup doesn't offer Touch ID again that boot; when `/dev/sep-bio` or the keybag never appeared, the activation never ran, and the error points to `journalctl -k`, the driver's own log. While the record exists, `omarchy-mac-touchid-load.service` (pulled in by a `multi-user.target.wants` link) loads `apple-sep` at every boot once `udevadm wait` sees `/dev/disk/by-partlabel/iBootSystemContainer`, since the driver opens that link as it probes and does not retry, and before the greeter and `fprintd`. The wait is part of the service rather than a device dependency, because systemd waits for a unit's devices before it checks its condition: a dependency would hold up every boot, agreed or not, and the greeter on a machine without the partition until the device timed out. A key store from an earlier load (`/var/lib/aurora-sep-keybag.bin`) is not agreement: that owner never saw this text, so they are asked too, told that the existing key store is used. `omarchy-lifecycle-dispatch disable-fingerprint`, after the fingerprints are deleted, removes the record and the options, so the driver stops loading from the next boot and the status offers Touch ID again; the key store stays. A record or options that can't be written, or removed, fails the operation rather than reporting success, and a carved calibration, like the sensor key, takes its name only once it is whole. On a kernel with omacom/linux-aurora#180, udev loads `apple_sep` on every Mac, read-only unless the options file exists, and a read-only driver always reports `matching` as `blocked`. The activation runs only on the owner's record, so a Mac whose owner hasn't agreed, or turned Touch ID off, keeps the boot's `available` and is offered Touch ID; and `enable-fingerprint` writes the options for a Mac agreed before they existed whatever its status, so one that reads `blocked` reaches `ready` after a restart. The Neo's sensor key (`apple/msrk-j700.bin`) is device-private, so nothing reads it before the owner agrees. asahi-installer copies this Mac's factory records (`com.apple.factorydata`) into the ESP's fallback firmware archive, `asahi/all_firmware.tar.gz`, on every install; an image install mounts the ESP at `/boot/efi` with `umask=0077`, so only root can read it there, and that mount is where the archive is read; on yes, `lib/touchid-root-key` (Python's standard library only) reads the `MSRk`, `seal` and trust bundle records from it in memory, rebuilds the key as omarchy-mac-installer's `factory_root_key()` does on macOS (the `MSRk` record's `IM4P` under the FDR sealing manifest, with the trust bundle as `secb`), checks its envelope, and refuses records that aren't all found byte for byte in this Mac's own iBoot System Container, so an archive from another Mac, or one swapped on the ESP, gives no key. It writes the key root-only (`0600`) under a temporary name, synced, then renames it. Nothing is kept when the owner says no, and a yes that then fails to turn Touch ID on takes back the key it rebuilt along with the agreement; `disable-fingerprint` deletes the installed key, and the next yes rebuilds it. A factory reset gives the factory root no key, since the ESP survives it and the next owner's yes rebuilds it. Every Neo install has the archive, since upstream asahi-installer writes it on every install, so none needs the installer to collect the key. A Neo without the archive (removed by hand) or without `python` reads `unsupported:no-root-key`; the boot status looks for the archive, so `omarchy-mac-touchid-status.service` runs after `boot-efi.mount`. Carved files under `/usr/lib/firmware/updates` belong to no package, so a root rollback can remove them. An agreed Mac isn't asked again, so its setup doesn't carve them back: turning Touch ID off (Omarchy's fingerprint removal) and on again does. The two operations, and `available`, need the matching Omarchy change before this file ships. `omarchy-mac-touchid-activate.service` (`lib/touchid-activate`) runs only on the owner's record, so it never opens a driver something else loaded without agreement (fprintd still opens `/dev/sep-bio` when it probes its readers, so on a kernel with omacom/linux-aurora#180, which loads the driver on every Mac, fprintd's allowance for the node needs the same gate first), and writes `/run/omarchy-mac/touchid`, `0644` so the session user can read it, and only when all four of the Secure Enclave driver's `diag` attributes say Touch ID can enrol and match, as the driver's ABI document asks: `touchid` reads `ready`, `sensor_attach` reads `attached`, `restore` reads `restored` or `empty`, and `matching` reads `usable` or `unverified`. `diag/touchid` alone can read `ready` while the sensor is uncalibrated, the enrolled fingerprints are unproven, or the xART guard blocks a match, as on a cold-booting M1-family Mac, and the invitation that follows comes only once. Anything else writes the reason instead (`failed`, `not-ready`, `unproven` or `blocked`) and says why in the unit's journal. Touch ID activates only on the first open of `/dev/sep-bio`, so `94-omarchy-mac-touchid.rules` starts the unit, which opens it once, read-only, as soon as the kernel publishes it; nothing needs enabling. The kernel activates Touch ID inside that open, and activation lasts the rest of the boot after the close. So does a failed activation, so the unit opens the node only once the kernel has made this Mac's keybag, `/var/lib/aurora-sep-keybag.bin`. The node takes one opener at a time, so a node `fprintd` holds is already activated. The attach retries once about 10 s after a short fall, so the script waits until 45 s after it starts for a settled answer, and `TimeoutStartSec=60s` bounds an open that blocks. A missing attribute ends it at once. An update runs it again, and a `ready` from earlier in the boot stands while `sensor_attach` reads `attached`, unless a final failure (`failed`, `unproven` or `blocked`) appears, since `diag/touchid` follows every later bring-up and one can fall short and recover. On the install or update that brings the rule, `/dev/sep-bio` already exists and no add event comes, and the boot-time status unit hasn't run on the update that first installs it, so `90-omarchy-mac-touchid.hook` starts the status unit and then the activation after the transaction, and the same session's post-update check sees the result. On a Mac with no agreement, that status run records `available` and the activation is skipped, whatever loaded the driver, unless Touch ID failed to come up earlier that boot: a reason that failure recorded (`failed`, `not-ready`, `unproven` or `blocked`) stands until a restart, and setup says to restart. The hook is skipped in a chroot, which includes `pacman --root`, or an unbooted root, and never fails the transaction: a unit that fails says why in its journal. The post-update fingerprint invitation then reaches the owner, and the fingerprint setup installs `libfprint-git`, whose aarch64 build carries the Touch ID driver (omacom/omarchy-pkgs#806) and owns `fprintd`'s allowance for `/dev/sep-bio`. systemd resolves that allowance when `fprintd` starts, so the drop-in `fprintd.service.d/50-omarchy-mac-touchid.conf` orders `fprintd` after `omarchy-mac-touchid-wait.service`, which follows the boot-time load, waits up to 15 s for the node where the Secure Enclave driver has a device and returns at once on a Mac without one, and after the activation, so `fprintd` never takes the node while the activation holds it: when both start together, at boot or from the pacman hook, `fprintd` waits for the activation, up to 60 s on a Mac whose attach is still settling. It adds no allowance of its own, and it's inert until Omarchy's setup installs `fprintd`. No sleep hook: the kernel ends a capture before suspend, and on a MacBook Neo the lock screen took the finger on the first touch after resume. Ship this file only once a boot without `aurora-touchid` shows enrolment, verification and suspend working, which still needs: Omarchy's `enable-fingerprint` and `disable-fingerprint` operations and their calls from the fingerprint setup and removal, since `apple-sep` is a module (`APPLE_SEP=m`: built in, it probes before udev has made the iBoot System Container's partition link and fails without retrying) with no modalias, which loads only on the owner's record; and m1n1 that forwards `/chosen/apfs-preboot-uuid`, which selects this install's own lane in the Secure Enclave. Keep that source stable: changing it (boot entries with and without `apple_sep.os_uuid_hi`/`os_uuid_lo`, or a stub reinstall) orphans the Linux enrolments. Without all of that the invitation, which comes once, leads to a setup that cannot finish. `lib/touchid-recovery` prints the passive JSON report the configuration transition reads before it changes a live Mac. It is installed at `/usr/lib/omarchy-mac/touchid-recovery`. The report names `action`, `node_present` and `facts` (`host_store`, `xart`, `sensor`, `touchid`, `sensor_attach`, `restore`, `matching`, `refusals`). `host_store` is `ready` only when `keystore` reads `open` and `keybag` reads `present`; `refusals` is the integer in `xart_guard_refusals`, or `-1` when that attribute is missing. `action` is `ready-for-test` only when the node exists and those facts show xART writes enabled, the sensor online, Touch ID ready, the sensor attached, a restored or empty enrollment, a usable or unverified match path and no guard refusals. `touchid` of `unknown` is `setup`. Anything else is `unsupported`. `lib/touchid-activate` follows the aurora kernel's naming (the `apple_sep` driver and its `diag` attributes): a kernel that renames them stops the invitation without an error, so move the script together with the kernel pin.
- `keyrings`: `asahi-alarm-keyring`, the signing keyring of the `[asahi-alarm]` repository. `omarchy update` reinstalls every installed keyring this file names, with Arch Linux ARM's, before the system upgrade, so an Asahi key rotation never fails that upgrade's signature checks.

omarchy-mac is the platform package on Apple Silicon: the recipe declares `provides=('omarchy-platform')` and `conflicts=('omarchy-platform')`, so only one platform package owns the root. Nothing may depend on `omarchy-platform`: the provide exists for the conflict, and a dependency on it could pull this package onto another machine.

Nothing is staged under `/usr/share/omarchy`, which belongs to the `omarchy` package. Ship this package with or before the runtime that reads the platform root: that runtime with an older omarchy-mac would lose the Mac's key names, notch cutouts, backlight choice and DDC skip.

The same directory holds the app hooks a runtime with the step 6 seam calls as the user: `post-install <app>` after an installer put the app in place (a Chromium-family browser gets user setup again, so its fresh flags file turns hardware decode off; Steam gets its FEX launcher through `sudo` and `omarchy-launch-steam --prepare`; other apps nothing), and `pre-remove <app>` before a remover takes it away (Steam: the FEX launcher, which depends on it, and the desktop entry the launcher wrote, unless the user changed it). Both refuse root; a failure fails the install or stops the removal.

The logind drop-in `/usr/lib/systemd/logind.conf.d/20-omarchy-mac-sleep-key.conf` keeps logind from suspending on the top row's moon key, which the kernel reports as `KEY_SLEEP` but is Do Not Disturb on a Mac; it applies from the next boot or logind reload.

Vendor defaults use NetworkManager's `/usr/lib/NetworkManager/conf.d`, systemd's `/usr/lib/systemd` and `/usr/lib/tmpfiles.d`, modprobe's `/usr/lib/modprobe.d`, and WirePlumber's `/usr/share/wireplumber/wireplumber.conf.d`. Same-name `/etc` or user fragments retain precedence. iwd has no vendor directory, so an `iwd.service` drop-in lists `/usr/lib/omarchy-mac/iwd` after `/etc/iwd`; iwd loads the first `main.conf` it can read, so an `/etc/iwd/main.conf` replaces the Apple one whole. The Apple default keeps iwd off 6 GHz: on the BCM4388 a join the firmware makes to a 6 GHz access point reports connected and authorized, yet the access point drops everything the Mac sends and DHCP never completes, so a network that also offers 5 GHz joins there instead. The firmware's own roaming can still move a weak connection onto 6 GHz, and `omarchy network band 6` cannot reach 6 GHz. Like the backend, it applies when iwd next starts: setup restarts nothing, so an upgraded Mac keeps 6 GHz until it reboots. Setup reports effective live NetworkManager/module configuration and systemd fragments. Review those reports and any drop-ins when diagnosing overrides; custom policy is never normalized to the package default.

## Video decode in mpv

mpv has no vendor configuration directory and decodes in software unless told otherwise. The package ships its Apple default as `/usr/share/omarchy-mac/mpv/mpv.conf` and a systemd-tmpfiles rule that copies it to `/etc/mpv/mpv.conf` only when that file is missing. pacman's systemd hook applies the rule when the package is installed or upgraded, and boot applies it again. An existing `/etc/mpv/mpv.conf` is never overwritten, with one exception: `omarchy-mac-setup-system` replaces a regular file byte-identical to the earlier default, which lacks `gpu-sw=yes`, with the current default, and leaves an edited copy or a link alone. An upgrade alone does not apply this, because neither `omarchy update` nor a pacman upgrade runs setup: run `sudo omarchy-mac-setup-system`, or rerun hardware setup, to apply it. So edit it rather than delete it to change the system default; each user's `~/.config/mpv/mpv.conf` is read after it and wins, and `hwdec=no` there decodes in software.

The default decodes H.264, HEVC and VP9 on the Apple Video Decoder with copy-back (`hwdec=vaapi-copy`, `hwdec-codecs=h264,hevc,vp9`) and draws with the OpenGL renderer (`vo=gpu`, `gpu-api=opengl`). On an M2 Max, copy-back is bit-exact against software decoding, and 1080p playback falls from about 55% to 13% of a core. Zero-copy (`hwdec=vaapi`) is not used: Asahi's Vulkan driver reads the imported chroma plane from the wrong offset, so gpu-next shows green frames, and `libva-v4l2_request` invalidates the frames of a decoder it closes, which copy-back has already copied out. gpu-next also costs about three times the CPU of OpenGL to upload copied frames. `libva-v4l2_request-avd` and `avd-fw` provide the decoder; without them mpv falls back to software.

On a Mac whose GPU has no driver yet, such as the M3 Max, the only OpenGL renderer is Mesa's software one: llvmpipe, or softpipe where Mesa is built without LLVM. mpv rejects a software renderer while probing, and mpv 0.41 then aborts with `vo_x11_init: Assertion '!vo->x11' failed`: its Wayland context does not clean up after a failed init, and the X11 context it tries next asserts on the leftover (fixed upstream in mpv-player/mpv@a58dd8ac41, not yet in a release). `gpu-sw=yes` lets mpv draw on llvmpipe or softpipe there instead. It changes nothing where the context mpv picks has a hardware renderer.

On an M3 Max, llvmpipe plays video but cannot keep up with it. These figures assume a Mesa built with LLVM (Arch's 26.2.3). Fullscreen on the 3456×2160 panel with mpv 0.41.0, 30-second 30 fps clips cost about 10.7 cores and drop 350 of 900 frames at 1080p H.264, and about 12 cores with 526 dropped at 4K H.264 or HEVC. Decoding goes to software: without a GPU render node libva cannot name its driver, so `vaapi-copy` fails over. Forced with `LIBVA_DRIVER_NAME=v4l2_request`, AVD decodes all three, and decoding alone falls from 0.23 to 0.08 of a core at 1080p H.264 and from 1.1 to 0.24 at 4K HEVC, but as many frames drop, because drawing is the cost. Current mesa-aurora is built without LLVM, so until omacom/omarchy-pkgs#1474 is resolved such a Mac gets softpipe, which draws a fraction of a frame per second: on a 13" M3 Air, about 0.2 fps at 1080p and 720p. mpv still plays rather than aborting.

## Battery charge limit

`omarchy battery charge limit [80|100]` shows or sets the `macsmc-battery` charge thresholds and refuses unless `omarchy-hw-apple-silicon` holds. It writes only the end threshold through `sudo`, since the driver derives the start threshold (80 restarts charging at 75; 100 restores full charging), and checks the SMC's readback. Full charging stays the default.

A set limit is saved as `CHARGE_CONTROL_END_THRESHOLD=` in `/etc/udev/macsmc-battery.conf`, the file asahi-scripts' own rule restores from, so both agree on one value. The package's udev rule runs `/usr/lib/omarchy-mac/battery-charge-limit-restore` when the SMC battery appears at boot; it reapplies a saved 80 or 100 on Apple Silicon and otherwise leaves the SMC alone. Nothing needs enabling.

## Keyboard function-key mode

The built-in keyboard binds to `hid_apple`, whose `fnmode` decides what the top row sends. Apple Silicon uses the kernel's default, `fnmode=3` (auto): Apple keyboards send mute, volume, brightness and media first with F1-F12 behind Fn, as in macOS, and the non-Apple boards `hid_apple` recognises (Keychron and similar) keep F-keys first. The package ships no `hid_apple` option and the desktop install leaf writes none on Apple Silicon, so any option the owner sets wins, whatever its file name. For F-keys first on the Mac, write `options hid_apple fnmode=2` to `/etc/modprobe.d/hid_apple.conf` and rebuild the boot image (`sudo mkinitcpio -P`, or `sudo omarchy-mac-boot-update` on a Limine Mac): `hid_apple` loads from the initramfs with the options it was built with.

The desktop keyboard migration runs `omarchy-mac-setup-keyboard` on upgraded Macs, naming the line Omarchy generated there according to the updating user's migration history: `fnmode=2` from the install leaf, replaced once by `fnmode=1` (quattro-upstream migration `1789132067`) or `fnmode=3` (mx-mac migration `1790305681`). While a fork migration still owes its rebuild, its own line is the generated one; a stock `fnmode=2` left by a fork run interrupted before it wrote its line looks the same as an owner's restored choice and stays. The first run retires `/etc/modprobe.d/hid_apple.conf` only when it holds exactly that line, keeping a `.omarchy-mac-retired` backup; any other file is the owner's and stays, and later runs, by any user, never retire. It then rebuilds the boot image once, including a rebuild the fork migration still owes, and switches the running keyboard to the configured mode. A failed or interrupted run retries both.

## Audio watchdog

`omarchy-audio-watchdog` (the user unit `omarchy-audio-watchdog.service`, enabled for every user) restarts PipeWire and WirePlumber when WirePlumber crashes or wedges at full CPU after asahi-audio's DSP filter chains are torn down, as they are at every logout. It restarts only while the screen is unlocked, stopping the shell first, within a restart budget it shares with the microphone mapper's `--repair`.

It is a stopgap for two WirePlumber bugs: [#1028](https://gitlab.freedesktop.org/pipewire/wireplumber/-/work_items/1028) (hide-parent never unhides a removed parent's id) and [#1029](https://gitlab.freedesktop.org/pipewire/wireplumber/-/work_items/1029) (removing a create-filter parent crashes or wedges WirePlumber). Exit criterion: remove the watchdog, its unit and its wants link once the WirePlumber that Macs install from Arch Linux ARM or asahi-alarm carries the fixes for both, and logging out and back in no longer wedges audio on an M1 and an M2.
