# omarchy-mac-boot

Apple Silicon boot support for Omarchy, packaged separately from the kernel-neutral `omarchy-mac` hardware package beside it. Its Arch recipe in [omacom/omarchy-pkgs](https://github.com/omacom/omarchy-pkgs) pins a full commit of this repository, takes its version from that commit's UTC date and stages this directory; the recipe keeps only packaging metadata and the pacman scriptlet.

It covers what stays on an installed Mac and runs again when the Mac updates. What runs once to produce the system, the macOS app and the Linux image, belongs to the [Omarchy Installer](https://github.com/omacom/omarchy-mac-installer).

`install DESTDIR` stages commands in `/usr/bin`, sourced modules/setup leaves in `/usr/lib/omarchy-mac/boot`, the lifecycle dispatch entrypoints in `entrypoints/` in `/usr/lib/omarchy/mac-boot`, and the initramfs, in-place encryption and first-boot payload in `files/` at its installed paths (mkinitcpio drop-ins, initcpio hooks, units, presets, the ALPM hooks and `/etc/default/update-m1n1`, which pins update-m1n1's device-tree order to the C locale). One ALPM hook rebuilds the initramfs when a drop-in changes; `11-omarchy-mac-saved-modules.hook` runs right after kernel-modules-hook puts the running kernel's modules back and, only after a kernel downgrade, moves them to `/usr/lib/modules/.old` as `linux-modules-cleanup` would at the next boot, so update-m1n1's `-ARCH` default gives m1n1 the installed kernel's device trees. It performs no live setup. Its presets and first-boot hand-off never enable `speakersafetyd`: omarchy-mac's `80-omarchy-mac-audio.preset` (#535) is its only owner, and an upgrade leaves existing enable links alone. A boot pin must therefore not publish ahead of an omarchy-mac pin that includes #535: until then no edge package presets speakersafetyd, and the image check refuses an image without it enabled. The recipe's `backup=` covers every `files/etc` path and `files/usr/lib/omarchy/initcpio`. `test/all` runs command fixtures and the payload's offline checks; `OMARCHY_DISPOSABLE_BOOT_TESTS=1` also builds real initramfs images and converts loop-device disks in privileged containers. Shared provisioning and reset integration is covered by `test/integration/` at the repository root, against the Omarchy runtime.

While first boot keeps the splash up, a laptop with its lid open shows it on the built-in screen only: `70-omarchy-mac-external-displays.rules` has `/usr/lib/omarchy/mac-boot/external-displays hold` force the Apple display card's external connectors off as the card appears, before Plymouth sees it. The lid is read from the kernel's lid switch (`/usr/lib/omarchy/mac-boot/lid-state`), since the card can appear before logind starts. Nothing is held on a shut or unknown lid, a desktop Mac or once the splash is over. `omarchy-mac-external-displays.service` turns them back on after Plymouth quits and owner setup or a password reset on tty1 ends, before the display manager starts, with a synthetic hotplug so the compositor rescans them. A held display may wake to a black console rather than stay asleep (the kernel console can light it before the hold), and a boot that never reaches multi-user.target keeps it off.

The implementation was moved from runtime integration `e82fe3c8850b184dfa22eefd571646ad85446122`, preserving Marcelo's provenance recorded in the runtime source-port ledger. The payload in `files/` comes from the boot recipe paired with #503 (omarchy-mac/omarchy-pkgs-aarch64#65 at `617a907f99a1`) with maralcbr/omarchy-pkgs#202 applied (omarchy-mac-boot 20260921-10: the owner's keyboard layout and dock keyboards at the disk prompt). The owner wizard, recovery-slot operations, journal/retry handling and shared Limine menu/hash operations remain core code. Hardware setup reaches its setup leaves through `omarchy-lifecycle-dispatch setup-boot [image-first-boot]` (`entrypoints/setup-boot`: `setup/grub-console.sh`, then `setup/limine-boot.sh`, which on an image's first boot asks for the deferred rebuild instead of building the UKI); the image builder sources them directly. `entrypoints/update-takeover <path>...` answers an update that wants to move aside files no package owns (the step 6 seam asks before it moves anything): read-only, it refuses the whole takeover when any path is the Mac's boot chain, `/usr/lib/initcpio` or pacman configuration, which its image and this package write, or an mkinitcpio file whose own `HOOKS` carry the `asahi` or busybox `encrypt` hook (a legacy Mac's unlock), and lets anything else go, including the memory, USB and mkinitcpio drop-ins omarchy-settings ships on aarch64 too. Owner provisioning, factory reset and `omarchy-drive-password` reach this package only through `omarchy-lifecycle-dispatch`, which runs the `entrypoints/` staged in `/usr/lib/omarchy/mac-boot` and fails on Apple Silicon when they are missing.

## Device tree overlays

A package can add a device tree node that the kernel's device trees do not have yet. Any package may ship one: a new SoC or a new device needs only a new `.dtbo` in that package's file list, never a change to omarchy-mac-boot. The package ships a compiled overlay as `/usr/lib/omarchy-mac-boot/dtb-overlays/PREFIX/NAME.dtbo`. omarchy-mac-boot owns that directory and ships it empty. It sits in `/usr/lib`, not `/usr/share`, because an overlay is architecture-specific binary data a tool reads, like the kernel's own device trees under `/usr/lib/modules` and firmware under `/usr/lib/firmware`. It is not in the platform root `/usr/share/omarchy-platform`, which belongs to the single platform package (omarchy-mac) and holds only what Omarchy reads. `PREFIX` selects the device trees: `t8103` selects every `t8103-*.dtb`, and `t6001-j316c` selects `t6001-j316c.dtb` only. `/etc/default/update-m1n1` sources `lib/dtb-overlays.sh`. When an overlay applies to one of the newest kernel's device trees, or to a device tree in a `DTBS` list set before the call, it sets `DTBS` to that list, with overlaid copies in `/run/omarchy-dtb-overlays` in place of the originals; a `DTBS` given as a directory is expanded the way `update-m1n1` expands it, before the overlays apply. The kernel files do not change, so pacman's mtree check still holds. The overlays apply in C order of `PREFIX/NAME`. An overlay whose root node has the string list `omarchy,skip-if-compatible` does not apply to a device tree that already has an available node with one of those compatibles (Linux's `of_device_is_available()`: no `status`, `okay` or `ok`). So a kernel that adds the node takes over from the overlay. An overlay whose root node has the string `omarchy,opt-in` applies only when that string is a line of `/etc/omarchy-mac-boot/dtb-overlays.opt-in`. Use it for hardware whose driver must not start until the owner chooses it. Editing that file rebuilds nothing: after opting in or out, run `sudo update-m1n1` and reboot. Until then the boot check reports `boot.bin` as stale, since it reads the opt-in list as it is now. If an overlay fails to apply, or dtc cannot read the result, that device tree stays as the kernel shipped it. With no overlays, `DTBS` keeps update-m1n1's default, and `boot.bin` does not change. Overlays need `dtc` (`dtc`, `fdtoverlay` and `fdtget`). The package that ships an overlay depends on it.

`omarchy-apple-silicon-boot-check` applies the same overlays when it rebuilds `boot.bin` for its comparison. Each overlay must belong to a package, or the check fails. It sources a copy of `/etc/default/update-m1n1` the way update-m1n1 does, under `/bin/sh` with `PATH=/usr/bin:/bin`, with the real library and the copies in its own workdir, so what it rebuilds is what update-m1n1 builds, and reading the configuration builds nothing. `dtb_overlays_update_m1n1` merges the overlays over the `DTBS` list it is called with, however it got there: the newest kernel's device trees, a list set above the call, or a directory, which it expands the way `update-m1n1` does. With overlays installed, a `DTBS` default it reproduces and dtc 1.7.1 or newer, the call always assigns `DTBS`, the expanded list even when no overlay applies to any tree in it, so a later `: ${DTBS:=…}` in the file no longer fires. A line after the call that overwrites `DTBS` leaves the overlays out: update-m1n1 builds the plain device trees, and the check does the same. A `boot.bin` still carrying the plain device trees from before the merge fails the check until `sudo update-m1n1` rebuilds it. Setting `OMARCHY_DTB_OVERLAYS=0` above the call turns the merge off, which the check follows without a warning. Where the call never runs, as with an edited copy pacman kept over the packaged one's `.pacnew` or a call in a branch that does not run, or where the file is missing, update-m1n1 leaves the overlays out, and so does the check, with a warning. `95-omarchy-mac-dtb-overlays.hook` runs `update-m1n1` when a package adds, changes or removes an overlay, as `95-m1n1-install.hook` does after a kernel update. So the next boot and the boot check read the same device trees. pacman reads its hooks when a transaction starts, so the transaction that first installs this hook does not run it: an overlay installed in that same transaction, with no kernel update beside it, reaches `boot.bin` at the next `update-m1n1` (`sudo update-m1n1`, or the next kernel update), and until then the boot check reports `boot.bin` as stale.

## Temporary adaptations

- Deploy ARM64 Limine to U-Boot's `EFI/BOOT/BOOTAA64.EFI` slot until the shared Limine installer supports that target.
- Retain the current GRUB-defaults-to-`rd.luks.*` command-line bridge while conversion, rekey and reset share that protocol. Switching to Limine does not itself change the initramfs unlock protocol. Removing this bridge requires coordinated conversion/rekey/reset qualification.
- Check factory-kernel coherence against the live boot partition because firmware, m1n1/U-Boot and DTBs are outside root snapshots. Generic root snapshot restoration alone cannot establish boot compatibility.
- Refuse a snapshot restore the live boot files do not match. `omarchy-mac-snapshot-check` is limine-snapper-sync's pre hook `04-omarchy-mac-snapshot-check` and post hook `99-omarchy-mac-snapshot-check`. Before the restore, a Limine Mac must be booted into the snapshot, and that root must pass `omarchy-apple-silicon-boot-check --boot-chain`: what the next boot reads, as `update-verify` checks it, with no reboot pending. The restore's own list can still put back another snapshot, so after it the restored `@` must hold the booted root's kernel, device trees, m1n1, U-Boot and Limine, and the UKI the restore put on the ESP must carry that kernel; otherwise it says not to reboot and how to put the backup back, and the pre hook lets that one undo through while the booted root fails its check, since the ESP then holds the refused root's boot files. The restored root must also carry the Limine activation, ESP, crypttab and root mount of the booted root. A restored root that cannot be read is reported unchecked and arms no undo. The pre hook sorts before the activation gate so a GRUB Mac is told why: Omarchy's restore is limine-snapper-restore alone, with no subvolume swap for GRUB. The hooks run from the booted snapshot, so they protect snapshots taken with this package or later.

Do not duplicate shared snapshot/UI/password policy here. Historical GRUB fallback remains for compatibility; this refactor qualifies fresh Limine images, not upgrades of old factory snapshots. Moving an existing Mac onto these packages is a standalone migration, outside this package.
